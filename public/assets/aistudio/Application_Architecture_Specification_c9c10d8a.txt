# 1. INTRODUCTION

## 1.1 Purpose

Application Architecture Specification (AAS) merupakan dokumen teknis yang menjelaskan struktur internal, teknologi, komponen, pengelolaan data, serta hubungan antarmodul dalam aplikasi NexaDesk.

Dokumen ini menjadi pedoman utama dalam proses pengembangan agar seluruh fitur dapat bekerja secara terintegrasi, konsisten, dan mudah dikembangkan.

NexaDesk dirancang sebagai aplikasi manajemen bisnis yang dapat digunakan oleh pemilik usaha kecil dan menengah untuk mengelola aktivitas operasional bisnis dalam satu platform.

## 1.2 Architectural Goals

Arsitektur NexaDesk memiliki beberapa tujuan utama:

1. **Modular:** Setiap modul memiliki tanggung jawab yang jelas dan tidak bergantung secara berlebihan pada modul lain.
2. **Consistent:** Seluruh halaman menggunakan sumber data yang sama sehingga perubahan data langsung tercermin pada bagian aplikasi yang relevan.
3. **Maintainable:** Struktur kode mudah dipahami, diperbaiki, dan dikembangkan.
4. **Scalable:** Arsitektur memungkinkan penambahan backend dan database pada pengembangan berikutnya.
5. **Reliable:** Operasi bisnis penting, seperti checkout dan pembatalan transaksi, harus menjaga konsistensi data.
6. **Local-first:** Data bisnis disimpan pada perangkat pengguna tanpa memerlukan server database.
7. **User-friendly:** Proses pengelolaan data, pencadangan, dan pemulihan harus mudah digunakan.

## 1.3 Architectural Scope

Versi awal NexaDesk merupakan aplikasi frontend-only.

Artinya:
- Tidak menggunakan backend server khusus.
- Tidak menggunakan database online.
- Tidak memerlukan koneksi internet untuk fungsi operasional utama setelah aplikasi tersedia.
- Data disimpan secara lokal menggunakan browser Local Storage.
- Seluruh proses bisnis dijalankan melalui TypeScript pada sisi frontend.
- Ekspor dan impor data dilakukan langsung dari browser.

Beberapa fitur eksternal, seperti AI Assistant berbasis Gemini, bersifat opsional dan memiliki keterbatasan keamanan jika diakses langsung dari frontend.

# 2. SYSTEM ARCHITECTURE OVERVIEW

## 2.1 Architecture Pattern

NexaDesk menggunakan pendekatan **Modular Frontend Architecture** dengan pemisahan tanggung jawab berdasarkan beberapa lapisan.

Arsitektur ini terdiri dari:

1. Presentation Layer
2. Application Layer
3. Business Logic Layer
4. Data Access Layer
5. Local Storage Layer

Setiap lapisan memiliki fungsi tersendiri agar kode tidak bercampur antara tampilan, proses bisnis, dan pengelolaan data.

## 2.2 High-Level Architecture

Alur komunikasi utama aplikasi:

User Interaction → Presentation Layer → Application Layer → Business Logic Layer → Data Access Layer → Local Storage.

Data yang diperbarui kemudian dikirim kembali melalui state management sehingga seluruh komponen yang membutuhkan data tersebut dapat diperbarui.

### Layer Responsibilities

**A. Presentation Layer**

Bertanggung jawab atas seluruh tampilan dan interaksi pengguna.

Contoh:
- Dashboard
- POS Interface
- Inventory Table
- Finance Dashboard
- Customer Management
- Reports
- Settings

Presentation Layer tidak boleh melakukan manipulasi Local Storage secara langsung.

**B. Application Layer**

Mengatur alur penggunaan fitur dan menghubungkan antarmuka dengan proses bisnis.

Contoh:
- Checkout Handler
- Product Form Handler
- Inventory Adjustment Handler
- Expense Creation Handler
- Data Import Handler

**C. Business Logic Layer**

Menangani aturan dan perhitungan bisnis.

Contoh:
- Menghitung subtotal dan total transaksi.
- Memvalidasi ketersediaan stok.
- Menghitung laba dan rugi.
- Menghitung nilai persediaan.
- Memproses pembatalan transaksi.
- Memperbarui statistik pelanggan.

**D. Data Access Layer**

Menjadi perantara antara aplikasi dan media penyimpanan.

Tanggung jawab:
- Membaca data.
- Menyimpan data.
- Memperbarui data.
- Menghapus atau mengarsipkan data sesuai aturan.
- Melakukan validasi struktur data.
- Mengelola backup dan restore.

**E. Local Storage Layer**

Merupakan tempat penyimpanan data utama NexaDesk pada browser pengguna.

Media penyimpanan:
- Browser Local Storage.

Seluruh data bisnis utama disimpan dalam satu struktur data aplikasi yang terorganisasi.

- Customers

POS merupakan modul yang menangani transaksi penjualan.

Tanggung jawab:
- Menampilkan daftar produk.
- Melakukan pencarian produk.
- Memilih kategori.
- Menambahkan produk ke keranjang.
- Mengubah jumlah barang.
- Menghitung subtotal.
- Menghitung diskon dan pajak jika diaktifkan.
- Memilih pelanggan.
- Memilih metode pembayaran.

Fitur:

- Category Management
- Supplier Management
- Stock In
- Stock Out
- Stock Adjustment
- Stock Return
- Low Stock Monitoring
- Inventory Movement History

- Penjualan menghasilkan Stock Out.

- Penyesuaian menghasilkan Adjustment.

- Revenue

Pengeluaran dan pemasukan lain di luar transaksi POS dicatat melalui entitas tersendiri.

# 6. DATA ARCHITECTURE

## 6.1 Data Storage Strategy

NexaDesk menggunakan Local Storage sebagai penyimpanan utama.

Key utama:

`nexadesk_data`

Seluruh data bisnis disimpan dalam satu objek JSON terstruktur.

Keuntungan pendekatan ini:
- Struktur data terpusat.
- Backup lebih sederhana.
- Import dan restore lebih mudah.
- Relasi antarentitas dapat dipertahankan.
- Tidak membutuhkan server database.

Namun, Local Storage memiliki keterbatasan kapasitas dan hanya tersedia pada browser serta origin yang sama.

Data tidak otomatis tersinkronisasi antarperangkat.

## 6.2 Root Data Structure

Struktur data utama:

## 6.4 Entity Relationships

Hubungan utama antarentitas:

- Product → Category
- Product → Supplier
- Transaction → Customer
- Transaction → Employee
- Transaction → Transaction Items
- Transaction Item → Product
- Inventory Movement → Product
- Inventory Movement → Transaction (optional reference)
- Expense → Expense Category
- Income → Income Category

Relasi disimpan menggunakan identifier, bukan menyalin seluruh objek terkait.

Pengecualian adalah snapshot pada Transaction Item untuk menjaga riwayat transaksi.

## 6.5 Data Integrity Rules

Aturan integritas data:

1. Setiap ID harus unik.
2. Harga dan jumlah tidak boleh bernilai negatif.
3. Stok produk tidak boleh negatif pada transaksi normal.
4. Transaction Item harus memiliki referensi produk yang valid.
5. Transaksi yang dibatalkan tidak boleh dihitung sebagai penjualan aktif.
6. Produk yang sudah memiliki riwayat transaksi harus diarsipkan, bukan dihapus permanen.
7. Perubahan stok harus memiliki catatan Inventory Movement.
8. Setiap perubahan penting harus memperbarui timestamp.
9. Data import harus melewati validasi sebelum mengganti data aktif.
10. Nilai total transaksi harus konsisten dengan perhitungan item, diskon, dan pajak.

# 7. STATE MANAGEMENT ARCHITECTURE

## 7.1 State Management Approach

NexaDesk menggunakan global state management agar perubahan data dapat diterapkan ke seluruh modul.

Pilihan yang direkomendasikan adalah Zustand atau React Context.

Untuk aplikasi dengan banyak modul dan operasi data, Zustand dapat digunakan agar pengelolaan state lebih terstruktur.

Global state menyimpan data operasional utama yang telah dimuat dari Local Storage.

## 7.2 State Structure

Contoh:

```typescript
interface AppState {
  data: NexaDeskData | null;
  isLoading: boolean;
  isSaving: boolean;
  error: string | null;

  initializeApp: () => void;
  refreshData: () => void;
}
```

Operasi bisnis sebaiknya dijalankan melalui actions atau services, bukan langsung dari komponen UI.

## 7.3 State Update Flow

Contoh perubahan data produk:

```text
User submits product form
          ↓
Product Form Validation
          ↓
Product Service
          ↓
Update Central Data
          ↓
Save to Local Storage
          ↓
Update Global State
          ↓
Refresh dependent UI
```

Dengan pendekatan ini, perubahan produk otomatis tercermin pada:
- Inventory
- POS
- Dashboard
- Reports

## 7.4 Selectors

Selector digunakan untuk mengambil dan menghitung data yang dibutuhkan komponen.

Contoh:
- selectActiveProducts
- selectLowStockProducts
- selectCompletedTransactions
- selectTotalRevenue
- selectTotalExpenses
- selectNetProfit
- selectTopSellingProducts

Perhitungan turunan sebaiknya tidak disimpan berulang kali sebagai data permanen apabila dapat dihitung dari sumber data utama.

# 8. CORE BUSINESS LOGIC

Bagian ini merupakan inti integrasi antarmodul NexaDesk.

## 8.1 POS Checkout Workflow

Saat pengguna menyelesaikan transaksi:

1. Validasi seluruh produk dalam keranjang.
2. Pastikan produk masih aktif.
3. Pastikan stok mencukupi.
4. Hitung subtotal.
5. Hitung diskon dan pajak jika berlaku.
6. Hitung total pembayaran.
7. Validasi nominal pembayaran.
8. Buat Transaction ID.
9. Buat transaksi dengan status completed.
10. Kurangi stok produk.
11. Buat Inventory Movement untuk setiap produk.
12. Simpan snapshot harga dan nama produk.
13. Perbarui global state.
14. Simpan perubahan ke Local Storage.
15. Tampilkan bukti transaksi.

Seluruh perubahan harus dilakukan sebagai satu operasi bisnis yang konsisten.

Jika penyimpanan gagal, aplikasi tidak boleh menampilkan transaksi sebagai berhasil.

## 8.3 Transaction Cancellation Workflow

Pembatalan transaksi tidak boleh menghapus transaksi.

Alur:

1. Pengguna memilih transaksi.
2. Aplikasi meminta konfirmasi.
3. Pengguna memasukkan alasan pembatalan.
4. Sistem memeriksa bahwa transaksi masih completed.
5. Status transaksi diubah menjadi cancelled.
6. Stok produk dikembalikan.
7. Inventory Movement bertipe return dibuat.
8. Dampak transaksi terhadap pendapatan dan laporan dikeluarkan.
9. Dashboard dan laporan diperbarui.

Sistem harus mencegah pembatalan berulang yang mengembalikan stok lebih dari satu kali.

## 8.4 Inventory Adjustment Workflow

Alur perubahan stok manual:

1. Pengguna memilih produk.
2. Pengguna memasukkan jumlah perubahan.
3. Pengguna menentukan jenis perubahan.
4. Sistem memvalidasi nilai.
5. Sistem menyimpan stok sebelumnya.
6. Sistem menghitung stok baru.
7. Sistem memperbarui produk.
8. Sistem membuat Inventory Movement.
9. Sistem memperbarui Dashboard dan Inventory.

## 8.5 Financial Calculation

Pendapatan penjualan:

`Revenue = Sum of completed transaction totals`

Total pengeluaran:

`Total Expenses = Sum of recorded expenses`

Pendapatan lain:

`Other Income = Sum of non-POS income records`

Laba bersih sederhana:

`Net Profit = Revenue + Other Income - Total Expenses - Cost of Goods Sold`

Perhitungan COGS atau Cost of Goods Sold menggunakan snapshot costPrice pada item transaksi yang valid.

Untuk menjaga konsistensi, pembatalan transaksi harus mengeluarkan transaksi terkait dari perhitungan Revenue dan COGS.

Cash Flow harus dihitung secara terpisah berdasarkan arus kas masuk dan keluar. Laba bersih tidak boleh dianggap selalu sama dengan perubahan saldo kas.

## 8.6 Customer Statistics

Statistik pelanggan dihitung dari transaksi completed yang memiliki customerId.

Informasi:
- Total Transactions
- Total Spending
- Average Transaction Value
- Last Purchase Date

## 8.7 Dashboard Calculation

- Total Revenue
- Total Expenses
- Net Profit
- Number of Transactions
- Sales Trends
- Top Products
- Low Stock Products

Perhitungan harus mengikuti filter periode yang dipilih pengguna.

# 9. LOCAL DATA PERSISTENCE

## 9.1 Storage Service

Seluruh akses Local Storage harus melalui `storageService.ts`.

Komponen UI dan business services tidak boleh mengakses Local Storage secara langsung.

Fungsi utama:

```typescript
getData()
saveData(data)
updateData(updater)
resetData()
validateData(data)
```

Fungsi tambahan:

```typescript
exportJSON()
importJSON(file)
createBackup()
restoreBackup()
```

## 9.2 Initialization

Saat aplikasi dibuka:

1. Periksa apakah data NexaDesk tersedia.
2. Jika tersedia, baca data.
3. Validasi struktur dan schemaVersion.
4. Jika valid, muat data ke global state.
5. Jika belum tersedia, buat initial data.
6. Jika data tidak valid, tampilkan recovery state dan jangan langsung menimpa data lama.

## 9.3 Save Strategy

Setiap perubahan data harus disimpan setelah validasi berhasil.

Strategi penyimpanan:
- Update data pada memory terlebih dahulu.
- Validasi hasil perubahan.
- Serialisasi data menjadi JSON.
- Simpan menggunakan Local Storage.
- Jika berhasil, publikasikan state baru.
- Jika gagal, pertahankan state sebelumnya dan tampilkan pesan error.

Untuk operasi bisnis yang melibatkan beberapa entitas, gunakan satu transaksi perubahan pada root data agar tidak terjadi kondisi setengah tersimpan.

## 9.4 Storage Limitations

Local Storage memiliki keterbatasan:
- Kapasitas terbatas.
- Data hanya tersedia pada browser dan origin terkait.
- Penghapusan browser data dapat menghilangkan data.
- Tidak mendukung sinkronisasi otomatis.
- Tidak cocok untuk banyak pengguna yang mengakses data bersama.

Aplikasi harus memberikan peringatan ketika penyimpanan gagal.

Untuk penggunaan dengan data besar atau kebutuhan multi-device, versi berikutnya dapat menggunakan IndexedDB atau backend database.

# 12. ERROR HANDLING

Aplikasi harus menangani kegagalan secara konsisten.

Kategori error:

**Validation Error**
- Form tidak lengkap.
- Harga tidak valid.
- Stok tidak mencukupi.

**Storage Error**
- Local Storage penuh.
- Gagal menyimpan data.
- Data tidak dapat dibaca.

**Import Error**
- File tidak valid.
- Schema tidak sesuai.
- Relasi data rusak.

**Business Logic Error**
- Transaksi sudah dibatalkan.
- Produk tidak tersedia.
- Pembayaran kurang.

Setiap error harus:
- Memiliki pesan yang mudah dipahami.
- Tidak menyebabkan data rusak.
- Memberikan tindakan lanjutan jika memungkinkan.
- Dicatat untuk debugging apabila diperlukan.

---

# 13. SECURITY AND DATA PROTECTION

Walaupun NexaDesk merupakan aplikasi frontend-only, perlindungan data tetap harus diperhatikan.

Ketentuan:
1. Jangan menyimpan password pengguna dalam bentuk plaintext.
2. Jangan menganggap frontend authentication sebagai keamanan produksi.
3. Jangan menyimpan API key Gemini permanen di source code.
4. Validasi semua data yang masuk melalui form maupun file import.
5. Hindari menampilkan data sensitif dalam log.
6. Konfirmasi tindakan berisiko seperti reset dan restore.
7. Sediakan backup sebelum operasi penggantian data.
8. Jangan mengeksekusi isi file import sebagai kode.

Penggunaan Local Storage berarti data dapat diakses oleh JavaScript pada origin yang sama. Karena itu, aplikasi harus menerapkan praktik pencegahan XSS dan tidak boleh menganggap penyimpanan lokal sebagai penyimpanan terenkripsi.

---

# 14. PERFORMANCE AND OPTIMIZATION

Aplikasi harus tetap responsif ketika jumlah data meningkat.

Strategi:
- Gunakan pagination pada tabel.
- Gunakan memoization untuk perhitungan yang berat.
- Hindari menghitung ulang seluruh laporan pada setiap render.
- Gunakan lazy loading untuk halaman yang tidak langsung diperlukan.
- Optimalkan gambar produk.
- Gunakan komponen yang dapat digunakan kembali.
- Hindari penyimpanan data berulang yang tidak diperlukan.
- Pantau ukuran data Local Storage.

Jika volume data berkembang besar, pertimbangkan migrasi penyimpanan ke IndexedDB.

# 19. FINAL ARCHITECTURE PRINCIPLES

Seluruh proses pengembangan NexaDesk wajib mengikuti prinsip berikut:

1. **Single Source of Truth:** Tidak boleh ada sumber data terpisah untuk modul yang menggunakan entitas sama.
2. **Separation of Concerns:** UI, business logic, state management, dan storage harus dipisahkan.
3. **Data Consistency:** Setiap operasi harus menjaga hubungan dan konsistensi data.
4. **Reusable Components:** Komponen umum harus dapat digunakan kembali.
5. **No Fake Functionality:** Tombol dan fitur yang ditampilkan harus memiliki fungsi nyata atau diberi keterangan sebagai fitur demonstrasi.
6. **Local-first:** Data operasional disimpan pada perangkat pengguna.
7. **Recoverability:** Pengguna harus dapat mencadangkan dan memulihkan data.
8. **Future-ready:** Arsitektur harus memungkinkan penambahan backend dan database.
9. **Maintainability:** Kode harus mudah dipahami dan tidak menumpuk dalam satu file besar.
10. **Business-oriented:** Setiap fitur harus mendukung kebutuhan operasional bisnis nyata.
